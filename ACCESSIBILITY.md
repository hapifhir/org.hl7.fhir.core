## Commitment

This project is mainly a library, not an application with its own user
interface. Its accessibility focus is on the HTML that it generates,
principally the resource renderings produced by `org.hl7.fhir.services.renderers`
(and the older `org.hl7.fhir.r5.renderers`). This HTML ends up in resource
narratives, implementation guides, the FHIR specification, and the user
interfaces of applications built on this library.

We aim to ensure that the HTML generated by the renderers supports the
creation of content that meets the
[Web Content Accessibility Guidelines (WCAG) 2.0](https://www.w3.org/TR/WCAG20/)
at Level AA, at least.

Our approach is to make the default HTML accessible wherever we can do so
without significantly degrading the usual user experience (e.g. semantic
markup, table headers, text alternatives for images, not relying on colour
alone).

Where meeting the guidelines would make the usual experience significantly
worse, the renderers provide an option - `RenderingContext.setWcagConformant(true)` -
that switches the generated HTML to a form that does meet them (e.g. fainter
alternating table backgrounds, italics instead of reduced opacity).
Applications that need to be WCAG conformant should set this option.

## Scope

### In scope

* HTML generated by the renderers (`org.hl7.fhir.services.renderers`,
  `org.hl7.fhir.r5.renderers`) and the supporting XHTML utilities
* Any HTML produced by other parts of the library for display to people

### Not in scope

* The validator's command line interface and other non-HTML outputs
  (JSON, XML, OperationOutcome content), whose presentation is the
  responsibility of the applications that display them
* The legacy renderers for earlier FHIR versions (`r4`, `r4b`, etc.), which
  are not actively maintained

### Responsibilities of consuming applications

The renderers produce HTML fragments, not complete pages. Whether the final
result is accessible also depends on the application that hosts them:

* The **CSS** used by the host must be set up correctly. The generated HTML
  relies on stylesheet classes (e.g. those in the IG publisher templates) for
  colour, contrast, spacing and table presentation, and contrast or focus
  problems introduced by host CSS cannot be fixed here
* The host page must provide the surrounding structure (page language,
  title, landmarks, heading hierarchy, skip links, keyboard navigation)
* The `wcagConformant` rendering option should be set where conformance is
  required

### Third-party content

Narratives and other HTML authored by people and carried in resources are
passed through as provided. Their accessibility is the responsibility of
their authors.

## Conformance Status

**Believed conformant, tested downstream.**

Conformance is not tested on the core library itself. It is tested on
published implementation guides that are built using these renderers, and
some of those IGs (e.g. [US Quality Core](https://github.com/FHIR/us-quality-core))
test as fully conformant to WCAG 2.0 and later. On that
basis we believe the generated HTML is conformant when used with correctly
set up CSS and page templates, but this is not a formal conformance claim for
any particular application that uses the library.

## Known Limitations

None currently known. Issues found in downstream testing will be tracked as
GitHub issues and listed here.

## Reporting an Accessibility Barrier

If you find HTML generated by this library that is difficult or impossible to
use with assistive technology, please
[create an issue](https://github.com/hapifhir/org.hl7.fhir.core/issues/new/choose)
and include "Accessibility" in the title. Helpful details include:

* The resource (or a minimal example) being rendered, and the renderer used
* Where the output is displayed (e.g. an IG page URL), so the host CSS can be checked
* The accessibility checker, browser and assistive technology (and versions) used
* What happened, and what you expected

If the problem is caused by host CSS or templates (e.g. an IG template),
please report it to the maintainers of that template instead.

Accessibility issues are treated as bugs, not feature requests.

## Contributor Requirements

When changing the renderers or other code that generates HTML, please:

* Use semantic HTML (headings, lists, `<table>` with `<th>`/`scope`)
* Provide text alternatives (`alt`, `title`) for images and icons
* Don't rely on colour alone to convey meaning
* Use CSS classes rather than hard-coded inline styles for colour and
  contrast, so hosts can control presentation
* Check the output with `wcagConformant` both on and off
