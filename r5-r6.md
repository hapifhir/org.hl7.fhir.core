# Migrating from R5 to R6

The R6 core Java code is a new set of modules, not a renamed copy of `org.hl7.fhir.r5`. Most of the
work in porting code across is mechanical — imports and accessor names — but there are two
structural changes that need to be understood first: the model is split across three modules with an
enforced dependency order, and every object in the model now carries a *model context*.

This document covers what changed in the Java code and why. It does not cover changes to FHIR
itself — for that, see the R6 specification.

> **Warning:** this code is experimental, and subject to further change as R6 itself is developed.

## 1. Packages and classes

R5 and every version before it shipped as a single module per version. `org.hl7.fhir.r5` held the
generated model classes, the parsers, the worker context, the FHIRPath engine, the renderers, the
terminology sub-system, conformance tooling and the comparison engine — all under one package tree
named after the version.

That had two problems.

The first is the version in the package name. Application code that only ever touches the model —
building a `Patient`, reading a `CodeSystem` — had to be recompiled and re-imported for every
release, even though the classes it used barely changed. The R6 model classes are therefore
*versionless*: they live in `org.hl7.fhir.model`, with no version in the package name, and the
version is a property of the instance (see the model context, below) rather than of the type.

The second is that the layering was not enforced. Nothing stopped a model class from depending on a
service, and some did: in R5, `Base` declared

```java
public List<Base> executeFunction(FHIRPathEngine engine, Object appContext, List<Base> focus,
    String functionName, List<List<Base>> parameters)
```

so the model classes had a compile-time dependency on the FHIRPath engine. Once that is true of one
method it is true of the whole module, and the model cannot be shipped, reasoned about, or made
thread-safe on its own.

R6 splits the code into three modules with a strict one-way dependency — **model &larr; services
&larr; standalone**:

**`org.hl7.fhir.model`** — the model itself. `Base`, the generated resource and datatype classes,
the JSON/XML/RDF parsers, and the utilities that are purely definitional (`CodeSystemUtilities`,
`ValueSetUtilities`, `ExtensionUtilities`, `StructureMapUtilities`). It knows nothing about a worker
context, a terminology server, FHIRPath, or rendering. Its packages are:

* `org.hl7.fhir.model` — `Base`, `Property`, `Factory`, `LogicalBase`, `BaseList`,
  `ValidationInformation`, and the model context classes
* `org.hl7.fhir.model.core` — the generated classes for the core specification
* `org.hl7.fhir.model.core.formats` — the object model parsers
* `org.hl7.fhir.model.utilities`, `.utilities.formats`, `.extensions`
* one package per add-on model the module carries code for: `.tools`, `.testing`, `.fml`, `.api`

**`org.hl7.fhir.services`** — the machinery that understands the model: everything that has to
resolve a definition or evaluate something against one. The FHIRPath engine, the element model,
conformance and profile tooling, the renderers, comparison, OpenAPI, SQL-on-FHIR, Liquid, and the
structure map engine. This is where `IWorkerContext` is *declared* — it has no implementation here.
These are the services that a server shares between threads, so they are written to be safe to share.
(with one proviso: snapshots must be generated before multi-thread use of the context begins)

**`org.hl7.fhir.standalone`** — a standalone `IWorkerContext` implementation and the pieces a
command-line application needs around it: `SimpleWorkerContext`, `BaseWorkerContext`,
`CanonicalResourceManager`, the filesystem-backed terminology cache, and the terminology client. A
server that has its own context implementation depends on model and services, and never on
standalone.

A useful consequence: if your code compiles against `org.hl7.fhir.model` alone, it has no opinion
about how definitions are resolved, and nothing to configure. If you depend on `org.hl7.fhir.services`,
then you must provide your own implemention of `IWorkerContext`.

The appendix has the import map.

## 2. The model context

Every `Base` in R6 carries an `IModelContext`. It answers two questions:

* which version of FHIR this instance is being used against (`getFHIRVersion()`)
* which resources may appear in this tree, and how each one is parsed and serialised
  (`getContextInformation()`)

The second is why it exists. In R5, support for *additional resources* — resources defined by an
incubator IG rather than the base specification (see
[additional-resources-r5.md](additional-resources-r5.md)) — was a process-global registry, with an
optional scoped `CustomResourceRegistry` to opt out of the global default. The default had to be
global because parsers are constructed in many places that cannot be passed a registry, including
inside the object model itself. That works, but it means the answer to "what resources exist" is a
property of the JVM, so two applications in one process cannot disagree, and a scoped registration
only holds for as long as every parser in the path was handed the registry.

R6 turns this inside out. The registration lives on the model context, and the object carries the
context, so the question is always answered relative to the tree being worked on: the parser used
for a contained resource is chosen from the context of the resource that contains it. Two
applications in one JVM can support different sets of additional resources, and neither can affect
the other.

### Getting a context

```java
// the shared context for the core spec plus the add-on packages the model module ships
// code for (tools, testing, fml, api). A singleton - do not register anything on it
IModelContext ctx = ModelContext.fullCoreContext();

// your own, if you have your own registrations to make
ModelContext mine = new ModelContext();
MyPackageRegistration.register(mine, false);
```

Parsers require one, and throw if it is null:

```java
Resource r = new JsonParser(ctx).parse(source);
```

### The rules

Every object in a tree must share the same context, or the tree must be uniformly context-free.
The model maintains that invariant for you, through four mechanisms:

* **Constructors.** Every class has both `new Patient()` and `new Patient(ctx)`. The no-arg form
  creates a context-free object, to be adopted when it is added to a tree.
* **`setModelContext(ctx)` is adoption-only.** A null argument is a no-op; the same or a compatible
  context is accepted; an incompatible one throws `FHIRException` rather than silently corrupting a
  tree that belongs somewhere else.
* **Setters cascade.** A setter stamps the value it is given with the owner's context.
* **`BaseList`.** Every repeating element's list is a `BaseList` bound to its owning object, not a
  bare `ArrayList`. It extends `AbstractList`, so every mutation path — `add`, `addAll`, iterators,
  `listIterator().set`, `subList` views — funnels through `add(int, E)`, and there is no way to
  insert an element without it being stamped. The list holds its owner rather than a context,
  because the owner is usually adopted after the list is created.

Two escape hatches:

* **`changeModelContext(ctx)`** forces a whole tree to the given context regardless of what it
  carries now — for moving a tree between contexts, giving a context-free tree one retrospectively,
  or (with null) detaching it ready for re-adoption. It walks every node, so it is a migration
  operation, not a hot path.
* **`assertModelContext()`** walks the tree and throws at the first node whose context differs,
  naming the path. It exists for tests and for debugging the invariant; it is far too slow for
  production use.

### Compatibility

Two contexts are compatible when they have the same set of registrations — not when they are the
same object. `ModelContextInformation` canonicalises its registration set into a string and interns
that to a small int, so after the first call on each side `isCompatible` is an int comparison. This
matters because the check is on the path of every adoption.

A context that is copied from another (the constructor that takes a `ModelContextInformation`)
starts out compatible with its source and shares its immutable registrations; registering something
new on the copy makes the two incompatible from that point on, which is the correct answer — objects
created under the copy are no longer usable under the original.

## 3. List accessors gained a `List` suffix

For a repeating element, the list accessors are renamed:

| R5 | R6 |
| --- | --- |
| `getIdentifier()` | `getIdentifierList()` |
| `setIdentifier(List<Identifier>)` | `setIdentifierList(List<Identifier>)` |
| field `identifier` | field `identifierList` |

Everything else about repeating elements is unchanged — `hasIdentifier()`, `addIdentifier()`,
`addIdentifier(Identifier)` and `getIdentifierFirstRep()` all keep their names.

The list returned is not a bare `ArrayList`: it is the owned `BaseList` described above, which stamps
everything added to it with the owner's model context. The distinct name marks that — a caller cannot
hold an unowned list and expect additions to it to reach the object.

Note that the rename cannot be applied as a blind search-and-replace, because `getXxx()` on a
*non*-repeating element keeps its name. The distinguishing question is the element's cardinality, not
the accessor's spelling. Nor does the presence of a `List` accessor by itself prove the element
repeats: the generator also emits one where an abstract ancestor (`CanonicalResource`,
`MetadataResource`) declares an element as repeating and the resource constrains it — in that case
`getXxxMax()` reports the real maximum, `getXxxList()` presents the single value as a list of at most
one, and `setXxxList()` throws if handed more than one.

## 4. Other changes to the `Base` API

### Copying

`copy()` and `copyValues()` now take an `EnumSet<CopyObjectOptions>` saying which of the
`Base`-level features travel with the copy:

```java
Patient p2 = p.copy(Base.COPY_ALL);   // also COPY_DATA (user data only) and COPY_NOTHING
```

The options are `USER_DATA`, `COMMENTS` and `VALIDATION_INFO`. This replaces R5's
`Base.setCopyUserData(boolean)`, which was a static `ThreadLocal` — a process-wide switch for a
per-call decision.

`assignValues(Base dst, EnumSet<CopyObjectOptions> options)` is new. It does exactly what
`copyValues` does, but it has the same signature at every level of the hierarchy, where `copyValues`
takes a different argument type at each level (`Base`, `DataType`, `HumanName`). A `copyValues` call
made through a `Base`-typed reference binds statically to `Base.copyValues` and never reaches the
leaf type; `assignValues` dispatches virtually, and each override casts to its own type to select the
right `copyValues`. Use it whenever you are holding `Base` references.

### The property API lost the hash parameter

R5 passed a precomputed name hash alongside the name. R6 does not:

| R5 | R6 |
| --- | --- |
| `getProperty(int hash, String name, boolean checkValid)` | `getNamedValue(String name, boolean checkValid)` |
| `setProperty(int hash, String name, Base value)` | `setProperty(String name, Base value)` |
| `makeProperty(int hash, String name)` | `makeProperty(String name)` |
| `getNamedProperty(int hash, String name, boolean checkValid)` | `getNamedProperty(String name, boolean checkValid)` |
| `getTypesForProperty(int hash, String name)` | removed |
| `children()` | `getChildren()` |
| `listChildrenByName(String name)` | `getChildValues(String name, boolean checkValid)` |
| `getChildValueByName(String name)` | `getSingleChildValue(String name, boolean checkValid)` |

`getChildValues` returns an immutable list that never contains nulls and is never itself null, and
accepts `"*"` for all children. `getSingleChildValue` returns null for no value and throws if there
is more than one.

### Version and type

* `getFHIRPublicationVersion()` — abstract, implemented by every generated class, returning
  `FhirPublication` — is replaced by `getFHIRVersion()`, which returns a `String` and gets it from
  the model context. The version is a property of the instance now, not of the class.
* `getResourceType()` returns a `String`. The `ResourceType` enumeration is gone: a closed enum
  cannot name an additional resource, and additional resources are a first-class concept in R6.

### Validation information

The inner class `Base.ValidationInfo` becomes the top-level
`org.hl7.fhir.model.ValidationInformation`, and `ValidationMode` becomes
`ValidationInformation.ValidationMode`. `hasValidationInfo()`, `getValidationInfo()`,
`getValidationInfoForProfile()`, `addDefinition()`, `isValid()` and `hasValidated()` keep their
names. `addValidationMessage()`, `hasValidationMessages()` and `getValidationMessages()` are gone —
validation messages no longer hang off model objects.

### Hooks in place of dependencies

`executeFunction(FHIRPathEngine, ...)` is gone; the model module has no compile-time dependency on
the FHIRPath engine. Where a service does need the model to be able to present itself differently,
the model declares a hook that returns null and the service overrides it:

* `asType()` — the typed equivalent of this object, for an element model `Element`. Returns null on
  the typed model.
* `getAsICoding()` — a coding view of this object, where one makes sense.

The element model lives in `org.hl7.fhir.services`, which the model classes cannot see, so these
are the seams it reaches them through.

## 5. Additional resources

An *additional resource* is a resource that is not in the base specification but is defined by an
incubator IG — `TestPlan` and friends in `hl7.fhir.uv.testing`, `StructureMap` in the mapping
language IG, and so on. [additional-resources-r5.md](additional-resources-r5.md) describes the R5
arrangement; the R6 shape is the same three steps, with the registry replaced by the model context.

### 5.1 Generate the code

The validator's hidden `ig-codegen` command generates a full model — classes, a `TypeFactory`,
JSON/XML parsers and a registration class — for the resources and logical models in one or more IG
packages, in the same style as the generated core classes. Pass `-fhir-version r6` to generate
against the versionless `org.hl7.fhir.model` classes:

```
java -jar validator_cli.jar ig-codegen \
  -fhir-version r6 \
  -package-name org.hl7.fhir.model.testing \
  -output      org.hl7.fhir.model/src/main/java/org/hl7/fhir/model/testing \
  -config      org.hl7.fhir.core.generator/add-ons-config-r6 \
  -test-package-name org.hl7.fhir.model.testing \
  -test-output       org.hl7.fhir.model/src/test/java/org/hl7/fhir/model/testing \
  hl7.fhir.uv.testing#current
```

* `-fhir-version` — `r5` (the default) or `r6`.
* `-package-name` / `-output` — the Java package and folder for the generated model.
* `-config` — the code generation configuration folder: `license.txt`, `configuration.ini`, and any
  adornment `.java` fragments. Use `add-ons-config-r6` for R6.
* `-test-package-name` / `-test-output` — optional; also generate a JUnit round-trip test that loads
  every example in the source package and checks it round trips json &rarr; xml &rarr; json.
* the trailing arguments are the package id(s) to generate from.

`<Jname>` is the capitalised last segment of the package name, so `org.hl7.fhir.model.testing`
produces `TestingRegistration`, `TestingJsonParser`, `TestingXmlParser` and so on. This is the same
generator that produced `org.hl7.fhir.model.tools`, `.testing`, `.fml` and `.api`, which is why
those packages look the way they do.

### 5.2 Register with a model context

The generated `<Jname>Registration` registers the resources, and their parsers, with *a* model
context — not with the process:

```java
ModelContext ctx = new ModelContext();
String pid = MyIgRegistration.register(ctx, false);
```

(`tools`, `testing`, `fml` and `api` are already registered on `ModelContext.fullCoreContext()`,
so they only need this if you are building your own context anyway.)

`overridesBase` says what to do about a name the base specification also defines: `true` means these
definitions win (which is the whole point of an incubator IG that redefines an existing resource),
`false` means the generated classes are used only for names the base specification does not define.
Registering a name that is already registered, without `overrides`, throws.

Because registration is per context, and `ModelContext.fullCoreContext()` is shared, you cannot
register on the full core context — build your own `ModelContext` for your own registrations.

Under the covers, `ModelContextInformation.registerResource` records the resource name, the package
it was generated from, and a `CustomResourceHandler` wrapping an `IParserFactory` that can make a
JSON or XML parser for it. The core parsers ask the context for a handler by resource name
(`getHandler(name)`), which is why a contained or Bundle-entry resource resolves correctly with no
plumbing at the call site.

### 5.3 Make the definitions available

Registration changes how instances are *parsed*; it does not change what the worker context knows
about their *definitions*. `<Jname>Registration.packages()` returns the versioned package id(s) the
code was generated from, so the application can load the same packages into its context:

```java
for (String pid : MyIgRegistration.packages()) {
  NpmPackage npm = pcm.loadPackage(pid);
  context.loadFromPackage(npm, loader, true);   // as a "master" package
}
```

Loading as a master package is what makes a version-less lookup of, say,
`http://hl7.org/fhir/StructureDefinition/TestPlan` resolve to the incubator IG's definition rather
than the base one, while a version-qualified lookup still resolves to the base specification.

Keeping the two in step matters: the generated code and the loaded definitions have to describe the
same resources, or instances will parse into classes the context cannot validate or render.

### 5.4 In the IG publisher

IG authors do none of the above — the publisher ships the generated code and does the registration,
package loading and renderer set-up itself, driven by a parameter in the IG. See
[additional-resources-r5.md](additional-resources-r5.md) and the
[ig-parameters code system](https://build.fhir.org/ig/FHIR/fhir-tools-ig/CodeSystem-ig-parameters.html).
