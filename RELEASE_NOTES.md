## Validator Changes

* Server Mode Fix: -autoLoadPackages loads the package that defines a canonical URL the validator doesn't have (it never did: the lookup failed with a ClassCastException, and then a NullPointerException, both swallowed)
* Terminology Change: the tx log (-txLog) records a request that got no response - a timeout, or a failed connection - with the error and how long it ran (it showed the request with nothing after it, so a request that held validation up for a minute went unnoticed)
* Observation New Validation Checks: warnings when an Observation (or component) doesn't fit its LOINC code - units of a valueQuantity that can't be converted to LOINC's example unit (EXAMPLE_UCUM_UNITS) or aren't units of what the code's PROPERTY measures (e.g. Urate [Mass/volume] in mmol/L, or a substance concentration as a count per volume); a Quantity with no UCUM unit when the code requires units (UNITSREQUIRED); a value of the wrong type for the scale (SCALE_TYP: Qn, Ord, Nom, Nar, Doc - a waveform as SampledData is fine for a Doc code); a panel (PanelType) with a value, or with no hasMember or component; an order-only code (ORDER_OBS = Order) that isn't a panel; and hints when effective[x] doesn't fit the code's TIME_ASPCT (a period for a point in time, a single time for a collection over a number of hours). The properties come from one $lookup per code, cached in the terminology cache (including that a code isn't known)
* StructureDefinition New Validation Checks: the same rules for profiles on Observation that fix a LOINC code (on Observation.code, a required slice of code.coding, or a component slice's code): a value[x] restricted to types that don't fit the scale, a fixed unit that doesn't fit the code, a unit system other than UCUM for a code that requires units, a panel that requires a value or prohibits both hasMember and component, an order-only code, and (hints) effective[x] restricted to types that don't fit the timing
* SNOMED CT New Validation Checks: SNOMED CT codes are checked against what SNOMED CT says about them, at the base (whatever the profiles): the kind of concept (semantic tag) against where it's used - a Condition.code that isn't a finding, disorder or situation (a hint when it's a procedure - coding by proxy), a Procedure.code that isn't a procedure (a hint when it's a finding or disorder), a body site that isn't a body structure, a Specimen.type that isn't a specimen, an AllergyIntolerance.code that isn't a substance, product or allergy, and a medication code that isn't a product (an error; a hint for a substance); an Observation.code (or component.code) that is a finding or disorder; a planned procedure (procedure context = Planned) with status completed; and laterality - the sides given by the code's site, the body sites, a laterality refinement and the laterality extension must agree, a side can't be given for a structure that doesn't have one, and a hint when a structure that has a side has none given. Inactive concepts aren't judged. The properties come from one $lookup per concept
* StructureDefinition New Validation Checks: the same SNOMED CT rules for the codes a profile fixes (on Condition, Procedure, Observation - including component slices - Specimen, AllergyIntolerance and the Medication resources): the kind of concept against the element, a planned procedure with its status fixed to completed, and fixed sides (code, body site, laterality extension) that don't agree, or a side for a structure that doesn't have one
* AllergyIntolerance and Condition New Validation Checks: negation codes - a code that says the patient doesn't have something (a SNOMED CT situation whose finding context is Known absent or No known, e.g. 716186003 No known allergy, or an inactive one such as 716184000 No known latex allergy; the IPS absent-unknown no-known-* codes): a warning when it is refuted, that this is understood as refuting the negative (that the patient does have it), and a warning when an AllergyIntolerance with one has a reaction. Codes that say there is no information (the IPS no-*-info codes, SNOMED CT 1631000175102 Patient not asked) get the same two warnings
* Terminology Fix: the R3 terminology client reports the HTTP status of an error from the server (it was always 0), so a code an R3 server doesn't know is recognised as an answer, and cached
* Terminology Fix: when a terminology server says it doesn't have the client's cache (tx-issue-type cache-id-unknown - it restarted, or the cache expired or was dropped), the client forgets what it thought the server had, starts a new cache, and makes the request again from scratch (once; the reason is logged). It used to send the dead cache-id with every request for the rest of the session, so a long-running validator (server mode) failed every terminology request after the server restarted. A request that still fails this way isn't remembered beyond the session, and a property lookup doesn't take it to mean the code is unknown
* Terminology Fix: $subsumes answers from the server are cached (they were asked again every time); $lookup can ask for designations
* Terminology New Validation Check: a warning when a coding has no version, but its code system says versionNeeded = true (CODESYSTEM_VERSION_NEEDED) - a version pinned by the value set or the expansion parameters doesn't count, since it's specific to that context and doesn't travel with the coding
