## Validator Changes

* Slicing: a pattern discriminator whose pattern is a Coding (or a CodeableConcept with a Coding) that only fixes userSelected can now be evaluated - userSelected was ignored, so the slicing was reported as 'cannot be evaluated' (#2511)

* Bundle reference resolution: the R5 rules for resolving relative references in a Bundle now apply to all FHIR versions. A relative reference (e.g. `Patient/123`) is only resolved against the fullUrl of the entry that contains it when that fullUrl is a RESTful URL. In a bundle with `urn:uuid:` fullUrls (common in R4 documents and messages) such references are reported as unresolvable (information), with a warning when an entry matches by type and id, and in documents they may now fail to resolve. The setting that controlled this (`-r5-bundle-relative-reference-policy` on the command line, the `r5BundleRelativeReferencePolicy` server parameter, and `ValidationOptions/ValidationEngine/InstanceValidatorParameters.get/setR5BundleRelativeReferencePolicy`) has been removed - passing it is now an error

* Terminology tests (`/txTest/setup`, `test-version`): can run the tests from the ci-build of a branch of the tx-ecosystem IG, `current$<branch>` - to test a server change against test changes that aren't merged yet

* Terminology cache: an $expand that fails without an answer about the value set is no longer kept for later runs, only for the rest of this one. As well as a server that couldn't be reached, that is now a 500 (INTERNAL_ERROR), a 401 or 403 (NOSERVICE), no server able to expand the value set (NOSERVICE), and a request that failed on this side (INTERNAL_ERROR). INTERNAL_ERROR results already written to a cache are dropped when it is loaded

* Terminology ecosystem: when the registry finds no server for a code system and says that it knows of no code system at all on its host (`unknown-host`, see 'Unknown Hosts' in the tx ecosystem IG), the registry isn't asked about any other code system on that host for the rest of the run

* Terminology: a code system from a loaded package (a dependency, not the IG being built or the files being validated) isn't sent to the terminology server (tx-resource) when the server's TerminologyCapabilities lists that version of it, with its content - it has it already. The IG publisher was sending the full ICD-10-CM (28 MB, from fhir.tx.support) to tx.fhir.org, which has the same version, once a run (PackageInformation.isFromNpmPackage)

## Other code changes

* FHIRPath: an evaluation can't run for ever - repeat() stops with an error after 1000 rounds (FHIRPathEngine.MAX_REPEAT_ROUNDS; 1.repeat($this + 1) never ended), and any evaluation stops with an error after a minute (FHIRPathEngine.MAX_EXECUTION_MILLIS, can be changed with setMaxExecutionMillis). Expressions come from content - invariants, Liquid templates, ViewDefinitions - and can be written so they don't end

* Liquid: a template can't nest for, if, capture and include more than 100 deep (LiquidEngine.MAX_DEPTH, counting the levels in included templates), when it's parsed or when it's run - a template that included itself went on until the stack ran out

* NpmPackage: a package that decompresses to more than 1.5 GB is refused by default (NpmPackage.DEFAULT_MAX_LOAD_SIZE; the largest real package, us.nlm.vsac#0.18.0, is 1.25 GB). There was no limit unless setDefaultMaxLoadSize was called, and nothing called it, so a decompression bomb could exhaust memory or disk. setDefaultMaxLoadSize(0) still turns the limit off

* NpmPackage: a package (tgz or zip) with two files of the same name is refused. Readers disagree on which copy wins, so a package with two package.json files could be one package to one reader and another to another. Names are compared after normalising ./, //, \ and Unicode form, and ignoring case (NpmPackage.entryNameKey), as FHIRsmith does

* NpmPackage: a package entry whose name has a .. segment is refused in every reader, with \ as well as / as the separator (NpmPackage.checkEntryPath). Extracting a tgz to disk (the package cache) only looked for /.. and ../, so package\..\x got through, and on Windows was written outside the package folder. The check is now by segment, so a name like Patient-a..b.json is no longer refused, and it throws IOException rather than RuntimeException. NpmPackageVersionConverter makes the same checks as NpmPackage (.. segments, duplicate names, the size limit)

* NPMPackageGenerator (services, r5, r4b, r4): adding a file whose name is the same file to some systems as one already added - they differ only in case, or in ./ or // (NpmPackage.entryNameKey) - is an error, and fails the build: every package reader now refuses a package with both. This happens when two resources' ids differ only in case. Adding exactly the same name twice is still a warning, and the second is skipped (PackageEntryNames). Files loaded from a folder (templates) were named with the platform's separator, so on Windows their tar entries had \ in them; they are named with / now

* ManagedFileAccess: setAllowedPaths() limits file access to the files under a set of folders. A path is checked where it really is (. and .. resolved, symbolic links followed), by path segments (so /ig-other isn't under /ig), and inStream(File) and outStream(File) are checked too. file(folder, name) and csfile(folder, name) check the file, not just the folder, and refuse a name that leads out of the folder (../..), whether or not access is limited. Code that uses java.nio.file.Files directly isn't checked

* Terminology logs (the IG publisher's qa-tx.html), in r4, r4b, r5 and R6: headers that authenticate a request or a session are masked like Api-Key, in the request and in the response - Authorization, Proxy-Authorization, Cookie, Set-Cookie, and any header whose name says it is about authentication, a session, credentials, a key, a token, a secret or a password (WWW-Authenticate and Proxy-Authenticate are kept). A server configured with token or basic authentication had its credentials written out in full, and in r4 and r4b nothing was masked. Header names are compared without the locale (in a Turkish one, COOKIE wasn't masked). The HTML log escapes the request line and the response's status line as well as the headers

* FileUtilities.clearDirectory, atomicDeleteDirectory, deleteAllFiles and deleteEmptyFolders never follow symbolic links (or Windows junctions): a link in the folder is deleted, not what it links to, and a folder that is itself a link isn't cleared (atomicDeleteDirectory deletes just the link). Some folders are never emptied, whatever asks and however they are reached (FileUtilities.whyNotSafeToEmpty): a file system root, a system folder at the top (/usr, /etc, /home, C:\Windows - not other folders there, such as /work), one directly in a system folder that holds only system folders, homes or drives (/usr/local, /home/x, /Volumes/x, C:\Program Files\x), some others (/var/lib, /var/log, /opt/homebrew, WSL's /mnt/c - not /var/ci or /opt/build), the user's home folder (or above it) and the standard folders in it, ~/.fhir/packages, the system temp folder (or above it), the current folder (or above it), and a git repository root
* ManagedFileAccess: the MANAGED policy (and IFileAccessor) is deprecated: it has never worked - there is no way to set the accessor - and temporary files can't be made under it. Use DIRECT, limited with setAllowedPaths, or PROHIBITED
* FHIRPath round(n) gives empty unless 0 <= n < 1000, and Quantity lowBoundary(n)/highBoundary(n) unless 0 <= n < 17 (a huge precision made a huge number - the same problem as GHSA-994m-hm9j-92v9); round()'s error message said power()
* FHIRPath and Liquid (r4, r4b, r5 and R6) share one budget per run, ExecutionLimits: time (60 seconds), how deeply a template nests (100), how big a collection can get (10 million items), and how long a string can get (10 million characters). When Liquid runs FHIRPath, the FHIRPath spends the template's budget (Liquid's context, which it passes as the app context, carries it - LimitedExecutionContext) instead of getting a fresh one each time. The time is checked inside slow functions (distinct(), union(), subsetOf()...) too, and strings made by +, & and replace() are checked before they're made. r4 and r4b get the repeat() round limit, the time limit and the Liquid nesting limit, which only r5 had. setMaxExecutionMillis(0 or less, or a huge value) means no time limit (a huge value overflowed, and every evaluation timed out)
* FHIRPath (r4, r4b): $this in repeat() is the item being evaluated (it was empty, so e.g. repeat($this.item) found nothing) - fixed in r5 in May, and not ported
* SQL on FHIR Runner (r4, r5, R6): each resource has a budget (ExecutionLimits), which the FHIRPath the view runs shares: 60 seconds (setMaxExecutionMillis), and no more than 100000 rows (setMaxRows) - each forEach multiplies the rows, so nested ones could make millions from one resource
* StructureMap transforms (r4, r4b, r5, R6): each transform has a budget, which the FHIRPath it runs shares: 60 seconds (setMaxExecutionMillis), groups calling each other no more than 500 deep, and no more than 1000000 rules (setMaxRules) - a map that calls itself never ended, and one that calls two groups each time ran out of memory. Variables is now the app context that carries the budget (new Variables() still works, without one)
* GraphQL (r4, r4b, r5, R6): a query can't nest selections or values more than 100 deep when it's parsed (graphql.Parser.MAX_DEPTH), and when it runs, it can't go more than 100 deep (a fragment that used itself never ended), take more than 60 seconds (setMaxExecutionMillis) or make more than 10000 lookups and searches (setMaxLookups) - nested searches multiply. The FHIRPath it runs shares the query's budget. The parser read `...` straight after a name as part of the name
* Test data factories (r5, R6): a factory run has one budget, which the Liquid templates and FHIRPath mappings it runs share - 10 minutes (TestDataFactory.setMaxExecutionMillis). A profile is walked no more than 100 levels deep (ProfileBasedFactory.MAX_DEPTH) - an extension that includes itself, and must be there, never ended
* FHIRPath (r4, r4b, r5, R6), review of the execution limits: join(), and making a collection into one string (evaluateToString(), and parameters given a collection), can't make a string longer than the run's limit; nor can encode(), escape() and unescape() (hex, or a \\ in json, doubles a string, so in repeat() there was no limit), or replaceMatches() (a regex that matches '' matches between every character - RegexTimeout.replaceAllWithLimit). ~, !~ and contains compare every item with every other, and memberOf and resolve() go to the terminology server or the host for each item: the time is checked as they go. split('') gave nothing, and went on until memory ran out: it now gives the characters (Utilities.simpleSplit), as Java and JavaScript do
* Liquid (r5, R6): each filter's value is checked as it's made (assign keeps a value, so a loop could double it each time round), and replace and join are checked before they make theirs. uniq and strip_html took as long as the square of the size of what they were given; they don't now (strip_html gives the same results as before). r4b: a statement whose value is a collection is checked as it's joined up
* SQL on FHIR Runner (r4, r5, R6): a column's values times the rows they go in is limited (10 million): a collection column could put millions of values in each of a hundred thousand rows
* StructureMap transforms (r4, r4b, r5, R6): append() can't make a string longer than the transform's limit (10 million characters) - append(s, s) in a group that calls itself doubled it each time - and the time is checked as each item a rule's source finds is processed. A source's log stops growing at 10 million characters
* GraphQL (r4, r4b, r5, R6): a query can't process more than 1000000 objects (setMaxObjects): fragments that each use the next one twice make 2^n from a query a few lines long
* Test data factories (r5, R6): a mapping expression that runs out of time stops the factory, instead of being logged as giving nothing
* Rendering profiles (r5, R6): PEBuilder, the StructureDefinition renderer's table view and Property.getXmlTypeName() no longer add an empty type to an element that has none (the root, or an element with a contentReference) - getTypeFirstRep() adds one when there isn't one, and the empty type then appeared in the profile wherever it went next
* TerminologyCache.clear() deletes only the cache's own files, not everything in the cache folder (which the user chooses)
* Validator -re-package: an output folder that isn't empty, and doesn't hold an earlier run's output (a manifest), isn't cleared - the run stops instead
* Package cache: a write that waited for another process to finish with a package no longer locks the lock file the other process moved away (both then thought they had the package, and the write failed with NoSuchFileException at the end); waiting ends when the lock file goes, not when anything in the folder is deleted; when the moved-away file it was waiting on is still locked, it tries again with the new lock file instead of failing; all its waiting is limited by the lock timeout; and the locks are always released, even when the write fails - or a read fails (a read that timed out, or found a lock file no process held, left the package locked, and every later write in the process waited for ever). The lock file now has the process id in it (it was meant to, but never did)
* NPMPackageGenerator.loadFiles: a symbolic link to something outside the folder being packaged is left out (with a warning) instead of its target's content being packaged, linked folders aren't followed when looking for ignore files, and files are read through ManagedFileAccess
* CompressionUtilities.unzip: an entry isn't written through a symbolic link (one already in the folder, or one an earlier entry made), each file is checked against the file access policy, and a target folder written with . or .. no longer refuses every entry

* NPM packages: a package loaded from a zip (a template from a github repository) can't have an entry with '..' in its name, the same as a tgz - unpacked, package/content/../scripts/ant.xml was written over scripts/ant.xml

* Snapshot generation: when a profile narrows the types of a type sliced element, the inherited type slices for types that are no longer allowed are prohibited (max = 0) in the snapshot, instead of being left usable - profiles no longer have to do this by hand (#1191)

* Snapshot generation: fix a StackOverflowError when a differential walks into an extension (and its children) inside an element reached through a content reference, e.g. Observation.component.referenceRange.low.extension.url - the walk into the Extension data type kept the content reference redirection (fhir-ig-publisher#1299)

* Snapshot generation: reslices are now checked against the slice they reslice - a slice whose reslices add up to more than its minimum gets SD_SLICE_MIN_EXCEEDS_SLICER (an error for publication), the same as slices against their slicer. The slicer's own check counts a resliced slice once (the larger of its minimum and its reslices' total) instead of counting the slice and its reslices separately, which over-raised the minimum of an auto-added slicing entry

* Snapshot generation: when a differential restates a type without aggregation or versioning - e.g. a slice on a Reference that narrows its target profiles - the aggregation and versioning of the same type in the base are kept, rather than dropped (#733)

* Snapshot generation: a differential that walks into an element with more than one type (without slicing it by type) and constrains anything other than its extensions now gets the error that says so - '... has children (...) and multiple types (...)' - instead of the generic 'No match found' for each child. It's a DefinitionException when the ProfileUtilities is set to throw exceptions (#2596)

* Snapshot generation: a min stated on a type slice is no longer reset to 0 after the slice is processed. That only happened when the type slicing entry was written out in the differential, so the same profile written with type specific names (valueQuantity) kept it (#2586)

* Terminology: a value set found on a terminology server is only taken when its url is the one asked for. A server that also returned value sets whose url starts with it (e.g. tx.fhir.org returning `...1267.39` for `...1267.3`) could have the wrong one chosen, and bindings rendered with a link to another value set

* Snapshot generation: a differential mapping marked with the elementdefinition-suppress extension now removes the matching inherited mapping (same identity and map) from the snapshot - it used to be ignored, so the inherited mapping was kept (#2669)

* Snapshot generation no longer rewrites the type of Resource.id in the base definition every time it generates a snapshot - that modified shared definitions, and raced when snapshots were generated concurrently (#2470). The fix (R4 publishes the fhir-type of Resource.id as 'string', not 'id') is now made once, when the definition is loaded from a package. Packages that are loaded without lazy loading now get all the package fixes too

* Package cache: `current$<branch>` packages (the ci-build of a branch) can now be installed - they were fetched, then refused as an illegal version - and are checked for a newer build of the branch, as `current` is. A branch name that isn't letters, digits, '.', '_' and '-' is refused before it's used to look in the cache or to fetch from build.fhir.org (current$../../x was fetched, and only refused afterwards)
